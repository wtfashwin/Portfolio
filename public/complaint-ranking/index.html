How complaint records become ranked problems

By Ashwin Upadhyay

The local pain-pipeline CLI groups complaint evidence before ranking it. This worked example follows the included fixture through duplicate detection, word overlap and scoring, so you can inspect what each count means.

All six input records are synthetic. The pain scores below are demonstration annotations. These records establish no customer demand, unique people, willingness to pay, payments or deployed app.

Start with six records, not six people

The frozen TOON fixture contains two identical CSV-export complaints, one longer CSV variant, two saved-link variants and one invoice complaint. Every record has kind: fixture; the source names are fixture provenance labels, not evidence of live collection.

  1. fixture_hn_1 and fixture_hn_2 both say “CSV export is broken when a field contains commas” and share https://example.com/fixtures/hn/1.
  2. fixture_forum_1 adds “and quotes” to the CSV complaint and has its own URL.
  3. fixture_reddit_1 says “My saved links are hard to organize by topic”; fixture_app_1 adds “and tags”. They have different URLs.
  4. fixture_forum_2 says “I lose track of invoices sent to my clients”.

The first pair collapses into one duplicate group. That leaves five deduplicated evidence groups. Similarity clustering then gathers those groups into three problems. Neither operation establishes how many distinct people experienced a problem.

First, join records that share a duplicate key

The deduplication implementation gives each record three keys: its exact ID, its canonical URL and its normalized text. Sharing any key joins records into the same group.

  • ID: IDs are compared as supplied, without a source namespace. Reuse of an ID across two sources can join their records. Choose IDs deliberately when preparing an import.
  • URL: the code parses the URL, removes its fragment and serializes it. For example, https://example.com/item#one and https://example.com/item#two share a URL key. Query strings remain: ?page=1 and ?page=2 are different URL keys, although an ID or text match can still join them.
  • Text: normalization applies Unicode NFKC, lowercases the text, replaces runs of nonletter/nondigit characters with a space, then trims the ends. Case and punctuation differences can therefore collapse. It does not remove stop words, stem words or recognize synonyms.

Key matching is transitive. If record A shares an ID with B, and B shares a URL with C, all three join even when A and C do not directly match. This groups connected evidence; it does not prove that the records came from the same person.

Each duplicate group gets one representative. The code first favors a normalized text variant supported by more distinct (ID, canonical URL) pairs, then breaks ties deterministically. Reimporting an unchanged record does not add another vote. In the fixture’s identical CSV pair, fixture_hn_1 is the representative; fixture_hn_2 contributes no extra mention.

Then compare sets of words

For each duplicate group, the representative’s normalized text becomes a set of unique words. The clustering step measures Jaccard similarity:

similarity = shared unique words / all unique words in either set

The short CSV complaint has nine unique words. Its longer variant adds “and” and “quotes”, so the pair shares nine words out of eleven in their combined set: 9 / 11 = 0.818181…. That exceeds the 0.65 threshold. The saved-link pair also shares nine of eleven words after “and” and “tags” are added.

The implementation visits representatives in a deterministic order. It places each one into the first qualifying cluster, provided its similarity is at least 0.65 against every existing representative in that cluster. If none qualifies, it starts a new cluster. This is greedy complete-link grouping, not semantic clustering or an exhaustive search for the best grouping.

Requiring every comparison prevents a chain from pulling dissimilar endpoints together. The existing test uses “alpha bravo”, “alpha bravo charlie” and “bravo charlie”: neighboring pairs score 2 / 3, but the endpoints score only 1 / 3. The result is two problems rather than one. See the similarity and chain regression tests.

Word overlap can miss paraphrases and can join wording that a human would separate. Review the underlying evidence before acting on a cluster.

Five mentions become three scored problems

The demo command supplies pain 8 to CSV problems and 6 to the others. It also supplies four-hour scope, regulated: false and hardware: false. These are synthetic demonstration annotations, not observed pain or a measured implementation estimate.

score = mentions × pain. Without a pain annotation, pain remains null and contributes zero to the score. Score ties use willingness to pay (wtp), then competitor gap (gap), then problem ID. Both annotations are null in this demo; they mean unknown, not measured zero. The comparator puts unknown values below supplied values. See the result fields and ordering.

Problem IDs and representative evidence

A problem ID uses the first 16 hexadecimal characters of a SHA-256 hash of its cluster representative’s normalized text. The evidence_ids field lists one representative ID per duplicate group, sorted by ID. It is not the full list of raw imported records.

A high score does not unlock selection. Eligibility separately requires a pain annotation, reviewed scope of at most eight hours, no regulated or hardware work, and exclusively live provenance. Fixture-only and mixed fixture/live clusters are blocked, including when a fixture and live record collapse into the same duplicate group. The annotation, eligibility and sorting tests cover these distinctions.

Reproduce the fixture locally

Use Node 24 and npm. Start in a directory where you can create a fresh clone, then check out the exact source revision used in this guide. Keep the included fixture unchanged.

git clone https://github.com/wtfashwin/pain-pipeline.git
cd pain-pipeline
git checkout --detach 03148aa9ae8579211081e9672108f13d7e502578
npm ci --ignore-scripts
npm run demo

The demo creates a fresh private local directory named runs/demo-… and prints its absolute path in the JSON root field. Repeat demos preserve earlier runs. To inspect the same run, replace the placeholder below with that printed path:

npm start -- status --run <printed-run-path>

The status should contain the three problem rows above and these fields:

{
  "imported_records": 6,
  "live_records": 0,
  "fixture_records": 6,
  "selected_problem": null,
  "real_users": 0,
  "spec_id": null,
  "app_id": null,
  "last_check": null,
  "deployment": null,
  "next_gate": "human_selection"
}

This is a selected field excerpt, not the complete status response. Reaching human_selection identifies the next workflow gate; it does not make fixture problems selectable. The demo stops without building or deploying a customer app.

Keep run directories and any private evidence local. The public example here contains only the shipped synthetic records and expected fields. See the pinned run instructions, evidence-storage limits and status implementation.

Review the evidence before selecting a problem

For an authorized live import, inspect the duplicate groups, URLs and complaint wording first. Check whether distinct IDs are accidental aliases and whether similar wording really describes the same problem. A mention is an evidence group, not a buyer, a person or a payment.

New records can change grouping, representatives and therefore problem IDs. After importing complaints or changing assessments, run rank again, inspect the current IDs and refresh annotations where needed. Selection must refer to the fresh ranking; an earlier selection does not carry over to a new ranking. The workflow binds selection to a ranking event.

Selection also does not establish demand. The later build-ready gate requires five distinct operator-attested live demand records. Those records remain separate from complaint mentions and are not independently verified users or payments. Read the live-run requirements and source policy before collecting real data.
